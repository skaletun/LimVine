# LimVine — архитектура

LimVine — игровой 3D-движок для low-poly игр: C++20, data-oriented ECS,
job system, собственный скриптовый язык **LV Script** с компиляцией в байткод,
Visual Scripting поверх него и редактор на ImGui.

---

## 1. Слои и правила зависимостей

```
                ┌──────────────────────────────────────────┐
                │  Editor (ImGui)  ·  Tools (lvrun, lvcook)│   прикладной слой
                └───────────────┬──────────────────────────┘
                                │
                ┌───────────────▼──────────────────────────┐
                │  Templates (farming_iso / rpg_3p / fps)  │   контент на LV Script
                │  stdlib/*.lvs (tween, fsm, pathfinding…) │
                └───────────────┬──────────────────────────┘
                                │
   ┌────────────────────────────▼─────────────────────────────────────┐
   │  Scripting: EngineBindings (ScriptWorld, BindingRegistry)        │   мост
   │             TemplateRunner · VisualScript (граф → LV Script)     │
   └──┬───────────────┬───────────────┬───────────────┬───────────────┘
      │               │               │               │
┌─────▼────┐   ┌──────▼─────┐  ┌──────▼─────┐  ┌──────▼─────┐
│ LV Script│   │   Render   │  │  Physics   │  │   Audio    │   подсистемы
│ (VM/GC)  │   │            │  │            │  │            │
└─────┬────┘   └──────┬─────┘  └──────┬─────┘  └──────┬─────┘
      │               │               │               │
      └───────────────┴───────┬───────┴───────────────┘
                       ┌──────▼──────┐
                       │  ECS / World│   ядро данных
                       └──────┬──────┘
                       ┌──────▼──────┐
                       │ Core: Math, │   фундамент
                       │  JobSystem  │
                       └─────────────┘
```

Правила:

1. **Зависимости идут только вниз.** `ecs` ничего не знает о `render`;
   `lvscript` не знает о движке вообще (это отдельная библиотека).
2. **Подсистемы общаются через ECS**, а не друг с другом напрямую: физика
   читает/пишет `Transform`, рендер читает `MeshRenderer`, звук — `AudioSource`.
3. **Скрипты — единственный «клей»**, которому разрешено трогать все подсистемы
   сразу; доступ выдаётся через capability-проверки в биндингах.
4. **Опциональные бэкенды** (Vulkan/OpenGL, Jolt, OpenAL, ImGui) скрыты за
   макросами `LV_WITH_*`; без них работают Null-бэкенды, поэтому весь код
   собирается и тестируется headless.

## 2. Почему ECS + data-oriented design

### 2.1 Архетипный Registry

`engine/ecs/Registry.h` хранит компоненты **пулами по типам** (SoA), а не
«объектами». Сущность — пара `{index, generation}`:

* `generation` делает handle безопасным: после `destroy()` повторное
  использование слота не даёт «оживший» объект;
* удаление — **swap-remove**: пулы остаются плотными, никаких дыр;
* итерация `each<A, B>(...)` идёт подряд по памяти, поэтому кэш-промахи
  минимальны даже на десятках тысяч сущностей.

### 2.2 CommandBuffer: отложенные структурные изменения

Системы (и скрипты) не имеют права создавать/уничтожать сущности во время
итерации — это инвалидировало бы пулы. Вместо этого изменения складываются в
`CommandBuffer` и применяются между фазами. Тот же механизм позволяет
безопасно вызывать скриптовые колбэки из середины системного прохода.

### 2.3 Фазы кадра

`World::tick(dt)` исполняет системы по фазам в фиксированном порядке:

| Фаза | Что происходит | Типичные системы |
|---|---|---|
| `Input` | опрос устройств, состояния действий | `input::InputSystem` |
| `Script` | планировщик корутин + `update(dt)` | `ScriptWorld::tick` |
| `Logic` | игровые системы C++ | геймплей |
| `Physics` | фиксированный шаг с аккумулятором | `physics::PhysicsWorld::step` |
| `PostPhysics` | чтение результатов симуляции | камера, триггеры |
| `Render` | culling → батчи → draw calls | `render::Renderer` |
| `Late` | UI, отладка | редактор |

Порядок важен: скрипт двигает персонажа **до** физики, физика **до** рендера,
а `PostPhysics` читает уже окончательные позиции.

## 3. LV Script: конвейер

```
.lvs ──Lexer──▶ токены ──Parser──▶ AST ──Compiler──▶ байткод (ObjFunction)
                                                          │
                                              ┌───────────▼───────────┐
                                              │  VM (стековая, NaN-box)│
                                              │  GC (mark-and-sweep)   │
                                              │  Scheduler (корутины)  │
                                              │  Sandbox (capabilities)│
                                              └───────────────────────┘
```

Ключевые решения:

* **NaN-boxing** (`Value`): число/bool/nil/указатель в одном 64-битном слове —
  никаких аллокаций на примитивы и никаких `std::variant`-накладных расходов.
* **Локалы в слотах кадра, стек — только для временных значений.** Это главное
  отличие от «классической» стековой машины, где локалы и есть стек. Следствие:
  `endScope()` освобождает слоты, но **не** выдаёт `Pop`, а `SetLocal` —
  peek-запись, требующая явного `Pop` там, где значение не нужно. Подробно —
  в `docs/03_lvscript_spec.md`, §4.6.
* **Единый контракт вызова**: результат всегда ложится в `argsBase - 1`
  (ячейка под аргументами), а `top` становится `argsBase`. Контракту следуют
  все четыре пути — `callClosureAt`, `callNative`, `callNativeMethod`,
  `callNativeFree`. Любое расхождение сдвигает стек вызывающей функции, и
  следующий вызов принимает предыдущий результат за callee.
* **GC без подсчёта ссылок**: mark-and-sweep с «pin» для интернированных строк
  и системных таблиц; шаг по бюджету, чтобы не давать пиков в кадре.
* **Песочница**: capability на каждый биндинг + топливо (счётчик инструкций)
  + лимит глубины стека + лимит памяти + белый список `import`.

## 4. Visual Scripting: граф как источник, код как представление

Blueprint-граф **транспилируется в LV Script** (`engine/scripting/visual/`),
а не интерпретируется отдельно:

* один язык отладки, один профилировщик, один hot-reload;
* сгенерированный код читаем и правится руками;
* round-trip: узлы несут метаданные `#@node`, поэтому граф восстанавливается
  из кода без потери позиций и связей.

Модель графа: **exec-рёбра** (порядок исполнения) и **data-рёбра** (значения).
Транспилятор обходит exec-граф, для каждого узла вызывает зарегистрированный
эмиттер (`flow.branch`, `flow.forRange`, `action.setPosition`, `pure.add`,
`event.update`, …), а data-рёбра превращает в выражения. Циклы в exec-графе
детектируются отдельно, чтобы не порождать бесконечную рекурсию.

JSON-формат графа обслуживает собственный мини-парсер (`JsonMini`), чтобы не
тянуть внешнюю зависимость.

## 5. Рендер: low-poly, батчинг, инстансинг

`render::Batcher` делает две вещи:

1. **Frustum culling** — отсечение по шести плоскостям до подачи в draw call;
2. **GPU instancing** — одинаковые меши с разными трансформациями сливаются в
   `InstanceBatch`, а статичная геометрия уровня — в `MergedChunk`.

Измерение из `tests/render_tests.cpp`: **4540 объектов → 438 draw calls**.
Для low-poly сцены это главный выигрыш: стоимость кадра определяется числом
draw calls, а не числом треугольников.

`GraphicsAPI` — интерфейс; `NullGraphicsAPI` позволяет прогонять весь пайплайн
без GPU (так работают CI-тесты и `lvrun`). Реальные бэкенды подключаются
макросами `LV_WITH_VULKAN` / `LV_WITH_OPENGL`.

## 6. Физика: интерфейс + детерминированный fallback

`physics::PhysicsWorld` — обёртка над Jolt (`LV_WITH_JOLT`). Без Jolt работает
встроенный симулятор: AABB-тела, raycast, `overlapSphere`, фиксированный шаг с
аккумулятором и защита от «спирали смерти» (`maxSubSteps_`), матрица
коллизий 16×16 слоёв.

**Кто владеет позицией** — критично для скриптов:

| Тип тела | Источник истины | Поведение |
|---|---|---|
| Static | `desc` | не двигается |
| Kinematic | `Transform` | `syncFromECS` берёт Transform и обновляет цель (`desc.position`) |
| Dynamic | тело | `syncToECS` **перезаписывает** Transform позицией тела |

Поэтому `setPosition()` из скрипта двигает и тело (`teleportBody`), а
персонажи под скриптовым управлением создаются кинематиками.

## 7. Многопоточность

`core::JobSystem` — пул потоков с очередью задач:

* `parallelFor(n, fn)` и `parallelForRange` — параллельные проходы по данным;
* используется батчером (culling по чанкам) и тяжёлыми системными проходами;
* `JobSystem::init(0)` — число потоков по числу ядер; в CI и headless-тестах
  допустим однопоточный режим, поэтому детерминизм не теряется.

Правило: задачи не имеют права структурно менять ECS (см. `CommandBuffer`).

## 8. Ассеты и горячая перезагрузка

`asset::AssetManager`:

* кэш по ключу `(путь, mtime, хэш)`;
* `FileWatcher` на polling'е (переносимо, без inotify-зависимостей);
* перезагрузка **каскадом по зависимостям**: изменение материала перезагружает
  связанные меши/шейдеры;
* колбэки reload — подписчик сам решает, что пересоздать.

`ScriptWorld::hotReload(path, newSource)` подменяет **тело прототипа**,
сохраняя объект `ObjFunction`: замыкания и инстансы продолжают на него
ссылаться, поэтому состояние (поля, upvalue, счётчики) переживает
перезагрузку. Это же делает возможным «живой» REPL в редакторе.

## 9. Тестирование

Десять self-test-сьутов, 294 проверки, все headless (`bash build_tests.sh`):

| Сьют | Проверок | Что покрывает |
|---|---|---|
| `lvscript_tests` | 53 | язык: лексика, выражения, классы, корутины, match, Result, песочница |
| `ecs_tests` | 13 | архетипы, поколения, swap-remove, CommandBuffer |
| `render_tests` | 15 | culling, инстансинг, батчи, frustum |
| `input_tests` | 17 | контексты, оси, мёртвая зона, сериализация привязок |
| `job_tests` | 6 | parallelFor, детерминизм |
| `visualscript_tests` | 31 | граф → код → граф, циклы, все типы узлов |
| `stdlib_tests` | 26 | tween/fsm/pathfinding/inventory/dialogue/quest |
| `engine_integration_tests` | 23 | скрипт ↔ ECS/физика/ввод/звук, hot reload, песочница |
| `template_tests` | 71 | три игровых шаблона «играются» из C++ |
| `editor_tests` | 36 | панели редактора рисуются в `TextUIDraw` и проверяются по содержимому |

Принцип: **тест обязан ловить регрессию, а не компиляцию**. Поэтому
`template_tests` не проверяет «скрипт загрузился», а сажает культуру,
прокручивает время, собирает урожай, ведёт диалог до выдачи квеста, стреляет
в врага и держит клавишу `W`, чтобы игрок реально сдвинулся.
